# 小米运动健康的数据怎么进来（跳绳 / 健腹轮）

**状态：导出这一步要你去做，我这边先把「看清楚格式」的工具做好了。**
原因写在最后一节，先说怎么做。

## 一、你去导出（大约 5 分钟）

1. 打开 **<https://account.xiaomi.com/>** 登录（手机号或邮箱）
2. 进 **隐私中心**（可能要再过一次验证）
3. 点 **管理您的数据**
4. 找到 **小米运动健康**，点右边的 **下载**
5. 按提示 **绑定邮箱**
6. 等它生成（数据量大的话要几分钟），**结果发到那个邮箱**
7. 邮件里是压缩包，**解压密码也在邮件里**

拿到 zip 之后，**不用解压**，直接跑：

```bash
bun scripts/xiaomi-inspect.mjs ~/Downloads/MiFitness_xxxx.zip
```

它会打印：压缩包里有哪些文件、每个 CSV 的表头、`Key` 列有哪些取值、
以及**运动类型那两列**（`sport_name` 里有「跳绳」「健腹轮」，`sport_id` 是编号）。

**把那段输出贴回来**，我再写解析器 —— 见最后一节。

## 二、⚠️ 已知的限制（先知道，免得以为是解析写错了）

小米官方导出**不是**一份完整的运动记录。第三方导出工具
（fitconverter）作者的实测结论：

> 小米运动记录可以导出全部的历史记录，可惜的是官方导出的数据**极其不全**
> （**无 GPS**，**只有零星的几个时间点有步频信息**），转换后基本上只能看看心率了。

⇒ 具体到**跳绳 / 健腹轮**：

| 大概能拿到 | 大概拿不到 |
|---|---|
| 场次（开始/结束时间） | 每一次的计数（120 个 / 15 个） |
| 时长 | 逐分钟的曲线 |
| 卡路里 | GPS / 距离 |
| 距离（如果器械报了） | 步频（跳绳的「每分钟次数」≈ 步频，但导出里很稀） |
| 心率（**只有戴着能测心率的东西时**） | |

⚠️ 所以「跳绳 120 个」这个数**很可能根本不在导出里**。它多半只在
小米运动健康 App 的界面上，而官方导出没有把它放进 CSV。
**这一点要等真的看到表头才能确定** —— 也正是下一节要做的第一件事。

## 三、⚠️⚠️ 为什么先「看」再「解析」

小米导出的 CSV 结构**随 App 版本变**，而我们手上**没有样本**。

照着别人的博客猜一套列名去写解析器，最可能的结局是**静默解析出 0 条** ——
而「0 条」和「那天真的没运动」**长得一模一样**。
这个项目为这件事栽过：`handleRebuild` 返回 202 而发布那段判 `status === 200`
⇒ **一次都没执行过**，而操作者收到的是**成功回执**。

⇒ 所以顺序是：

```
① 你看真实输出          → ② 拿真实几行当夹具 → ③ 写解析器 → ④ 断言数出来的条数
   （x iaomi-inspect）      （不能编）            （对着夹具写）    （0 条必须红）
```

**②③④ 都还没做，因为 ① 还没有。** 这不是偷懒 —— 是这一步没做的话，
后面三步都是猜的。

## 四、接进来之后大概长什么样（先想清楚，不是现在就写）

数据进来要回答三个问题，每个都不小：

1. **和三星/Health Connect 那些重复怎么办。**
   同一场跳绳，小米记一次、三星可能也记一次（如果你也戴着表）。
   `mergeSessions` 现在是**按 `start` 精确匹配**去重的 —— 而两边的
   开始时间**不会逐秒相同**。⇒ 需要「按时间重叠」合并，而 `SyncWorker`
   在手机端已经有这套逻辑（`sessions` 的注释里写着那次的教训）。
2. **`exerciseType` 怎么映射。** 服务器那边存的是 Health Connect 的数字编号；
   小米给的是自己的 `sport_id`。两边**不是同一套编号**，需要一张对照表 ——
   而且要有断言守着（漏一个类型的表现是「那类运动不见了」，不报错）。
3. **走哪条路进来。** 现在 chealth 的链路是
   `Health Connect → Health Sync → CEVTUO Health app → 服务器`。
   小米导出是**完全另一条路**（邮箱 zip、手动、一次性）。
   ⇒ 最可能是：写一个**导入脚本**，把 zip 解析成会话后
   `POST` 到 `/api/chealth`，和手机那条路**汇进同一个 store**。
   ⚠️ 那条接口是「窗口内以 incoming 为准」的，发之前要确认它不会
   把手机推的其它场次挤掉（`mergeSessions` 的注释里有完整理由）。

⚠️ 这三件都要**先有真实数据**才谈得上做对。
